# MS-4004.X — Talent / HR Hands-On Lab
### Acme Bottling · Microsoft 365 Copilot

**Audience:** Talent and HR team members — recruiters, HRBPs, L&D, people ops — who already use Copilot and want to move faster on hiring, onboarding, and employee comms.

**Format:** ~65 minutes of hands-on

**Level:** Intermediate. We skip the basics and get straight into real Acme Bottling work.

You're hiring a **Logistics Coordinator** for Acme's Midwest DC. You'll build a fair interview guide, onboard the hire, and announce a change people actually read.

> **How to use this lab:** Just read and follow along. Nothing to install, no repo to download, no code to save. Open the files linked below and go.

---

## What you'll be able to do

- Turn a role description into a structured, bias-checked interview guide.
- Build a 30-60-90 onboarding plan from rough, unstructured manager notes.
- Turn a skills gap into a prioritized, realistic learning path.
- Announce a change across three channels without the meaning drifting, then prepare
  managers for the questions it will actually provoke — including the ones with no good
  answer yet.
- Build reusable prompts for interview guides, onboarding, learning paths, and comms.
- Keep a validation habit so nothing affecting a person's job goes out unreviewed.

## Learning arc

This lab moves in one direction: **hire fairly, then set the person up to succeed.**

|  | **Exercise 1 — From role description to a fair interview guide** | **Exercise 2 — Onboard and communicate** |
|---|---|---|
| **You're doing** | Building a hiring instrument | Building the first 90 days, then landing a change people actually read |
| **Copilot's job** | Extract competencies, draft questions and rubric | Structure messy notes, prioritize gaps, draft comms, predict the hard questions |
| **Your job** | Decide what's job-related and fair | Decide what's policy, what's TBD, and what you won't pretend to know |
| **Stakes** | External — a real candidate is scored on it | External — a new hire and a whole team read it |
| **You leave with** | A defensible interview guide | Four people-facing artifacts + a 4-prompt library |

Every task runs the same beat: **prompt → read it critically → keep what's reusable.**
Every exercise ends the same way: **Source / Assumptions / Risk / Human check.**

## What this means when it affects someone's job

In HR the stakes are a person's hiring, pay, or standing. Copilot drafts and organizes; a
human reviews anything that touches a person's job — including the bias check, which is
yours to make, not Copilot's. Every exercise ends with source, assumptions, risk, and who
signs off.

# Exercise 1 — From a role description to a fair interview guide

**Objective:** Build an interview guide where every question maps to a competency in the
requisition, with a scoring rubric and a bias pass applied.

**Scenario:** Acme Bottling is hiring a **Logistics Coordinator** for the Midwest DC. You
need a fair, consistent interview guide today, built straight from the role — not from
memory.

### Task 1 — Set your HR voice and unpack the role

First you'll tell Copilot how to write for HR, then pull the competencies out of the req.

You'll use **Researcher** for this — a specialized agent that runs multi-step research
across the web and your work data and returns an answer with citations, instead of the
single-pass reply a normal chat prompt gives you. Here you want the multi-step reading of a
dense document, **not** the reach: everything this guide claims has to come from the
requisition in front of you.

1. Open **Copilot Chat** and go to **Settings** (gear icon or your profile picture, top
   right) → **Personalization**.
2. Add this **custom instruction** and save:

   ```
   When I work on HR content: write in plain, inclusive English. Keep bias out of hiring
   language, avoid jargon, and make drafts easy for a stakeholder to edit. For anything
   sensitive (hiring, performance, pay, personal data), add a short note on what a human
   must review before it's used.
   ```

   *No Personalization option in your tenant? Paste this block at the top of your first
   prompt in each exercise instead.*
3. In Copilot Chat, open **Agents** in the left sidebar (or the agent picker above the
   prompt box) and select **Researcher**.
4. Attach `AcmeBottling_Role_Description.docx` using the paperclip icon next to the prompt
   box.
5. Paste this prompt and press Enter:

   ```
   Using ONLY the attached role description, identify the 5–6 core competencies this role
   is really testing for. For each, note must-have vs nice-to-have and why it matters.
   List anything vague that should be clarified before we interview.
   ```

6. **Researcher may ask you a question before it runs** — often whether to weigh the
   requisition against outside hiring norms or market benchmarks. That's the agent doing
   its job. Here the answer is always **stay in the attached document**: this guide has to
   be defensible against *this* requisition, not against the market. Reply that, or
   **"go ahead"** if it only asks about formatting.

7. Jot down the competencies — they're the backbone of the guide.

> **Why this matters:** Competencies come from the requisition, not from memory. That's
> what makes the guide consistent across every candidate and defensible later.

> **If Researcher isn't available in your tenant,** it's licensed separately from Copilot
> Chat in some setups. Run the same prompt in a normal **Copilot Chat** thread with the
> requisition attached — you lose the multi-step reading, but "use ONLY the attached role
> description" is the part that's doing the work here, and it still holds.

### Task 2 — Build the structured interview guide

A guide is only fair if it's the *same* guide for every candidate. That's what the rubric
buys you — without "what strong vs. weak looks like" written down in advance, five panelists
score five different interviews and call it a consensus.

1. **Copy the competency list from Task 1** out of the chat. Researcher often treats each
   run as a fresh research task, so it won't reliably carry its own earlier answer forward.
2. **Stay in the same Researcher chat** and paste the prompt with the competencies under it:

   ```
   Create a structured interview guide from the competencies below. For each: one
   behavioral question, one follow-up probe, and a simple 1–3 scoring rubric with what
   "strong" vs "weak" looks like. Keep questions job-related and free of bias. Add a short
   intro script and a closing that invites candidate questions. Competencies:

   [PASTE THE COMPETENCIES HERE]
   ```

3. Read it once for structure: does every competency have a question, a probe, and a rubric?

### Task 3 — Pressure-test the guide for bias

Copilot wrote the guide, so Copilot is exactly the wrong judge of it — which is why the
prompt doesn't ask "is this biased?" It asks for something checkable: *which competency does
each question test?* A question that can't answer that is the one to look at hardest.

1. **Copy the interview guide from Task 2** out of the chat first. Researcher often treats
   each run as a fresh research task, so "the guide you just wrote" can come back as *"I have
   the competencies but not the interview questions."* Handing it back is faster than arguing.
2. **Stay in the same chat** and paste the prompt with the guide underneath it:

   ```
   Review the interview guide below. For each question, state which competency from the
   role description it tests. Flag any question that is not clearly tied to the role, that
   could touch age, family status, health, national origin, or personal life, or that a
   candidate without insider knowledge couldn't answer. Suggest a replacement for each one
   you flag. Guide:

   [PASTE THE GUIDE HERE]
   ```

3. Remove or rewrite anything flagged. **This is a first pass, not an approval** — a human
   still owns the final read.

> **Seeing stray `a { text-decoration: none; }` style text in an answer?** That's Researcher
> leaking the CSS behind a formatted table. Ignore it and copy the content — it isn't part of
> your guide.

### Validation checkpoint

In a scratch doc, answer for this guide:

- **Source:** Which file did Copilot use? Did it stay inside it?
- **Assumptions:** Did it invent any requirement not in the role description?
- **Risk:** What's the harm if a biased or off-topic question slips through?
- **Human check:** Who signs off before this is used with a real candidate?

> **Exercise 1 output:** a competency-mapped, bias-checked interview guide you could hand
> to any panel member.

# Exercise 2 — Onboard and communicate

**Objective:** Produce a 30-60-90 plan with every unknown flagged rather than invented, a
prioritized learning path, a change message that works in three channels, and a manager Q&A
that answers the hard questions honestly instead of reassuring past them.

**Scenario:** The hire is made. Now you need an onboarding plan from a manager's messy
notes, a learning path to close the new hire's skills gap, and a clear announcement for a
change that's coming — a new order-tracking dashboard.

### Task 1 — Turn messy notes into a 30-60-90 plan

The notes are deliberately incomplete, and one gap is marked TBD. Watch what Copilot does
with it — filling a blank with a plausible-sounding policy is the single most damaging thing
it can do in HR, and it will look completely normal on the page.

1. Open `AcmeBottling_Onboarding_Notes.docx` in **Word** — press **Start** and type *Word*,
   or use the app launcher (the grid icon, top-left) in Microsoft 365 on the web — and skim
   it (systems, people, early wins, and a TBD gap). Close it when you're done reading.
2. Create a new **Word** document, then **Create a copy → Create a copy online** → your
   **`Acme - HR Lab`** folder → name it **`Logistics Coordinator 30-60-90`**. On the **Home**
   tab, click the **Copilot** button (lower right corner or right of the ribbon).
3. In the prompt box type **`/`** and pick **AcmeBottling_Onboarding_Notes** — that hands
   Copilot the file instead of you pasting its contents. Then add:

   ```
   Turn the referenced notes into a clean 30-60-90 day onboarding plan for a new Logistics
   Coordinator. Organize into three phases with: goals, access/systems to set up, people
   to meet, and the expected "early win" for each phase. Flag anything marked TBD or
   unclear as an open item to confirm with HR — do not invent policy details.
   ```

4. **Where the answer lands depends on your version of Word.** Some builds draft straight
   into the document — if so, review it and click **Keep it** (or **Regenerate** /
   **Discard**). If the answer stays in the Copilot pane instead, click **Insert** under the
   response, or **Copy** and paste it into the page. Either way, nothing is final until you
   accept it.
5. Confirm Copilot flagged the **week-1 compliance training "TBD"** as an open item
   instead of inventing one.

> **Why:** Inventing a policy detail is the single most damaging thing Copilot can do in
> HR. "Flag, don't invent" is the instruction that prevents it.

### Task 2 — Turn a skills gap into a learning path

A gap list ranks itself by size. A learning path has to rank by *what matters and what a
person can actually absorb while doing their job* — so the prompt names both the priority
rule and the realism constraint, rather than leaving either to Copilot's judgment.

1. Open `AcmeBottling_Skills_List.csv` in **Excel** — press **Start** and type *Excel*, or
   use the app launcher (the grid icon, top-left) in Microsoft 365 on the web — and skim
   current vs target levels and priorities.
2. On the **Home** tab, click the **Copilot** button (lower right corner or right of the
   ribbon), then paste:

   ```
   Using ONLY this skills list, recommend a prioritized 90-day learning path. Focus first
   on High-priority gaps with the biggest level difference. For each, suggest a practical
   way to build the skill (on-the-job task, short course, or mentor pairing) and a simple
   way to tell it's improving. Keep it realistic for someone also doing a full-time job.
   ```

3. Sanity-check: does it lead with the High-priority, biggest-gap items (order-tracking,
   Excel analysis, data-quality habits, Copilot basics)?

### Task 3 — Draft the change communication, then fit it to each channel

Same message, three channels. This is where most HR comms time actually goes — and the
failure mode isn't tone, it's drift: a talking point softens a date, a Teams post drops a
caveat, and now three versions of one change are circulating.

1. Open `AcmeBottling_Employee_Comm_Brief.docx` in **Word** — read the change, the
   audience tone notes, and the structure to match. Close it when you're done reading.
2. Create a new **Word** document, then **Create a copy → Create a copy online** → your
   **`Acme - HR Lab`** folder → name it **`Order Tracking Change Announcement`**. Click
   **Copilot** on the **Home** tab, type **`/`** in the prompt box and pick
   **AcmeBottling_Employee_Comm_Brief**, then add:

   ```
   Draft an employee change-announcement using the referenced brief. Match this structure:
   1) What's changing (1–2 sentences), 2) Why it helps you, 3) What we need from you,
   4) Timeline & support, 5) Where to ask questions. Tone: warm, plain, no jargon;
   acknowledge people are busy and change-weary. Under 200 words.
   ```

3. **Stay in the same Word Copilot pane** and adapt it without changing the meaning:

   ```
   Turn the announcement into two short versions: (a) manager talking points for a team
   huddle, and (b) a 3-line Teams channel post with a clear call to action. Keep the
   meaning identical; just fit each channel.
   ```

4. **Stay in the same pane** and turn the broadcast into an exchange — this is the half of
   employee engagement that most change comms skip entirely:

   ```
   Now write the manager's Q&A sheet for this change: the eight questions a frontline team
   is most likely to ask, including the uncomfortable ones about workload, job security,
   and what happens when the new system goes down. Give an honest answer to each. Where the
   honest answer is "we don't know yet" or "that's still being decided," say that instead of
   reassuring. Mark any answer HR must confirm before a manager says it out loud.
   ```

5. Read the uncomfortable ones first. If every answer is soothing, the sheet is worthless in
   the room — push back in the same pane: *"Rewrite any answer that avoids the question, and
   any answer that promises something the brief doesn't actually commit to."*

> **Why this matters:** An announcement tells people what's changing. Engagement is what
> happens in the twenty minutes after, when a manager gets asked something the announcement
> didn't cover. Copilot is genuinely good at predicting those questions and genuinely bad at
> admitting uncertainty — so "we don't know yet" is something you have to ask for by name.

### Task 4 — Save your prompt library

This req is this req. The prompts are for every hire, every onboarding, every change after
it.

1. Create a new **Word** doc titled **"Acme HR — Prompt Library"**.
2. Paste in the four prompts from the
   [Prompt Library](#prompt-library-your-leave-behind) section below.
3. Save it somewhere you'll actually find it again.

This is your leave-behind. Swap in the next req or the next change and reuse.

### Validation checkpoint

- **Source:** Did the plan, path, and message each stay inside the file you gave Copilot?
- **Assumptions:** Did Copilot invent a policy, a benefit, a date, or a training
  requirement — or answer a Q&A question more confidently than the brief allows?
- **Risk:** What's the harm if a new hire follows an invented policy detail on day one, or a
  manager repeats a Q&A answer HR never approved?
- **Human check:** Who signs off before this reaches the hire and the wider team?

> **Exercise 2 output:** a 30-60-90 onboarding plan with open items flagged, a prioritized
> learning path, a change announcement in three formats, a manager Q&A sheet that admits
> what isn't decided yet, and a 4-prompt library.

## Prompt Library (your leave-behind)

Save these four. Anything in `[BRACKETS]` is a blank you fill in — delete the brackets too.
If you're stuck on one, use what you did in this lab: `[ROLE DESCRIPTION]` → *the Logistics
Coordinator requisition*, `[SKILLS FILE]` → *AcmeBottling_Skills_List.csv*, `[TIMEFRAME]` →
*90 days*, `[WORD COUNT]` → *200 words*. Where it says **PASTE**, paste the actual text in.

**1. Interview guide**
```
Using ONLY [ROLE DESCRIPTION], identify the core competencies, then build a structured
interview guide: one behavioral question, one follow-up, and a 1–3 rubric per competency
with what "strong" vs "weak" looks like. Keep questions job-related and bias-free. Add an
intro script and a closing. Then map each question to its competency and flag anything not
clearly tied to the role, anything touching [PROTECTED GROUND — e.g. age, family status,
health, national origin, personal life], or anything an outsider couldn't answer.
```
*"Using ONLY" is load-bearing. Drop it and Copilot benchmarks against the market, and your
guide stops being defensible against **this** requisition.*

**2. Onboarding plan**
```
Turn the notes below into a [TIMEFRAME — e.g. 30-60-90 day] onboarding plan: goals,
systems/access, people to meet, and an early win per phase. Flag anything TBD or unclear as
an open item to confirm with [WHO OWNS IT — e.g. HR] — do not invent policy.
Notes: [PASTE NOTES HERE]
```
*Then go check the TBDs yourself. "Flag, don't invent" only helps if somebody reads the
flags.*

**3. Learning-path recommendation**
```
Using ONLY [SKILLS FILE], recommend a prioritized [TIMEFRAME] learning path. Lead with
[YOUR PRIORITY RULE — e.g. high-priority gaps with the biggest level difference]. For each:
a practical way to build it (on-the-job task, short course, or mentor pairing) and a simple
way to tell it's improving. Keep it realistic for someone also doing a full-time job.
```
*The realism clause is what stops Copilot handing a new hire forty hours of coursework in
their first month.*

**4. Change communication (and channel adaptation)**
```
Draft an employee change announcement from the brief below. Structure: what's changing,
why it helps you, what we need from you, timeline & support, where to ask questions.
Tone: [TONE — e.g. warm, plain, no jargon; acknowledge people are busy and change-weary],
under [WORD COUNT]. Brief: [PASTE BRIEF HERE]
Then adapt it into [FORMATS — e.g. manager talking points for a huddle and a 3-line Teams
post with a clear call to action], keeping the meaning identical. Only the format changes.
Then write the manager's Q&A sheet: the [N] questions this audience is most likely to ask,
including the uncomfortable ones about [THE THINGS PEOPLE ACTUALLY WORRY ABOUT — e.g.
workload, job security, what happens when it breaks], with an honest answer to each. Where
the honest answer is "we don't know yet," say that instead of reassuring. Mark any answer
HR must confirm first.
```
*"Keeping the meaning identical" is the guardrail on the middle section. Without it, the
Teams version quietly drops the caveat and the huddle version softens the date. The Q&A is
the part people skip — and it's the only part that survives contact with a real team.*
